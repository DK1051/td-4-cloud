What I checked by running code (all in the scratchpad; nothing in the repo was changed except this file):
- **The cannot-do steps against a fake `az`.** I took the three `run:` blocks out of `cannot-do.yml` and ran each with `bash -e`, the shell GitHub uses by default. A fake `az` on PATH returned set outputs, and each output included a dummy secret text so I could see whether it leaked:
  - (a) Command succeeded → `FAIL: a deployment to westus should have been denied…`, exit 1. Nested `(DeploymentFailed)` … `Code: RequestDisallowedByPolicy` … `allowed-locations` → `PASS`, exit 0. `RequestDisallowedByPolicy` from another assignment → `FAIL: refused with RequestDisallowedByPolicy, but not by the expected rule (allowed-locations)`. `StorageAccountAlreadyTaken` → `FAIL: failed for another reason: (StorageAccountAlreadyTaken)`. Failure with no code → `FAIL: failed for another reason:` (empty list of codes).
  - (b) The object ID was decoded from a fake token and masked (`::add-mask::`) before first use, and the scope was masked as well. Command succeeded → FAIL. `AuthorizationFailed` → PASS. `PrincipalNotFound` → FAIL "another reason".
  - (c) Command succeeded → FAIL. `AuthorizationFailed` → PASS. `ResourceGroupNotFound` → `FAIL: group missing or identity can read the subscription`. `ExpiredAuthenticationToken` → FAIL "another reason".
  - In all 12 runs the dummy secret text never appeared in the script's output. Only error codes in brackets were printed.
- **4E assignment name.** `4e-canada-landing-zone/README.md` assigns the location policy under the name `allowed-locations`, so check (a)'s `REQUIRE_ALSO=allowed-locations` matches the 4E setup. The owner-tag policy will not trip check (a), because the step passes `owner=cannot-do-test`.
- **API version claim.** I built scratch copies of `main.bicep` with bicep 0.48.1. `2026-06-01` gave no warning. `2026-07-01` and `2026-09-01` gave `BCP081`. The fallback `2025-06-01` gave no warning. This matches the comment in `main.bicep` and the README's fallback advice. Whether Azure accepts `2026-06-01` in `canadacentral` stays `TODO(verify)`, as already logged.
- **Compiled output.** The compiled JSON has exactly one output, `storageAccountName = [variables('storageAccountName')]`, and no resource ID.

Minor findings (none is a FAIL; all are cheap or can stay as notes):
1. **The deploy workflows do not use the pinned Bicep.** `deploy.yml` and cannot-do check (a) run `az deployment group create --template-file main.bicep`, which compiles with whatever Bicep the runner's `az` picks. The pin applies only to the CI build step. This is outside G1 as written, and the API version compiles cleanly on both 0.48.1 and newer versions, so the risk is low. A possible fix is the same two lines (`az config set bicep.use_binary_from_path=false`, `az bicep install --version v0.48.1`) before each deploy. Suggest a CAVEATS line.
2. **The CI version check is loose.** `az bicep version | grep -q '0\.48\.1'` would also accept `0.48.10` or `0.48.1-preview`. This is a nitpick. The step just before it installs exactly v0.48.1, so in practice it only catches a wrong binary being used.
3. **One wording problem in `OIDC-SETUP.md` Step C.** The bold note says "Check this format on the GitHub docs page **above**", but the page's URL only appears in the next sentence. "below" or "linked here" would be accurate. The test checks for this exact text, so changing it means updating the test too.
4. **`REQUIRE_ALSO=allowed-locations` is a substring match,** so `allowed-locations-rg` would also match. This is harmless: the resource-group location policy cannot refuse a storage account deployment.
5. **The repo `README.md` still lists 4H as "Planned".** Brief step 10 has the director change it after the verifier passes, so this is still to do, not a defect. The 4H README already says the project stays "Built" until Eojin's runs.
6. **`docs/RUN-SHEET.md` already says "DONE (PR #4)".** Check the number once the PR is open.

Code Eojin may find hard to explain (AI judgement; cover in T4-C1): `<<<"$out"` here-strings; `set +e` … `code=$?` … `set -e`; a function call with an env-var prefix (`REQUIRE_ALSO=… verdict …`); `exit 1` inside a sourced function, which stops the whole step; the `grep -oE` pattern with three alternatives for codes; the base64 padding line `"=" * (-len(part) % 4)`; the reason for `bicep.use_binary_from_path=false`; and why (c) treats `ResourceGroupNotFound` as a failure (Azure checks permission before it checks existence).
