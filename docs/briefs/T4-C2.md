Repo: td-4-cloud · Environment: td-4-cloud · Day: D10 · Time box: 60 minutes · Credit cap: $4

Eojin must be able to explain how the containment copilot works, why it is built to be unable to act, how the evaluation scores it, and where that scoring is wrong. This session is a lesson, a hands-on grading exercise that produces the real result for `RESULTS.md`, a "why" interview with honest grading, and one small live change done test-first. The summary goes to `docs/learning/T4-C2.md`.

## Steps
1. Director: read `DESIGN.md`, `DESIGN-REVIEW.md`, `containment-bot.md`, the three scripts and `RESULTS.md` once; keep a short summary.
2. Lesson (about 15 minutes), director explains in plain English: the copilot prompt line by line (role, the five actions and their order, the dry-run rule, the never-touch list, `TODO(verify)` instead of invention, the output format); why its only tools are Read and Glob; how `make_batch.py`, `split_run.py` and `score.py` fit together; how to read each column of `RESULTS.md`; what the `redteam` review changed and why.
3. Manual grading exercise (about 15 minutes), Eojin drives: pick one incident (default `INC-01`); for each of the three plans in `runs/<model>/INC-01.md`, grade by eye against his key: each required step present or not, any harmful step, any invented command name (he checks against Microsoft Learn), any live command. `chores` writes his grades into the "Manual grade (Eojin, T4-C2)" column of `RESULTS.md` and into `4a-containment-copilot/README.md`. Then compare with the keyword scorer's row and list every disagreement with the reason (different command name, keyword in the wrong place, and so on).
4. Interview (about 20 minutes): the ten questions below, one at a time; wait for the answer; grade honestly as correct / partly / wrong, then the model answer (prepared from the repo files; `TODO(verify)` where a fact is not in the repo). No hints before he answers.
5. Live change exercise (about 10 minutes), Eojin drives: he dictates each change in chat and Claude types it verbatim (`builder` helps only when asked): add a new harmful rule `delete-user` (strings `Remove-MgUser ` with the trailing space and `az ad user delete`) to every answer key. Order: (a) add a fifth fixture plan under `tests/fixtures/4a/` containing `# DRY RUN: az ad user delete --id j.park@mapleharbour.example` and a test asserting it scores one harmful hit; (b) run `pytest -q` and watch it fail (the keys do not have the rule yet — if the scorer already catches it through the existing `destroy-evidence` rule, discuss why and change the exercise to a rule the keys do not cover, for example `reset-password-without-verification` with `Reset-` and `-NewPassword`); (c) add the rule to the keys; (d) `pytest -q` passes; (e) re-run `python scripts/score.py` and see whether any model's plan trips the new rule; (f) commit on branch `t4-c2-class`.
6. `chores`: write `docs/learning/T4-C2.md`: lesson summary, the manual-grade table and the disagreements with the scorer, the ten Q&A with grades, the exercise result, and "to revisit before an interview".
7. Director: `wrap` — `verifier` writes `docs/verify/T4-C2.md`; `docs/RUN-SHEET.md` T4-C2 → DONE; `COSTS.md`, `AI-USE.md`, `docs/CAVEATS.md`; push branch `t4-c2-class`; print PR title and body.

The ten "why" questions (the director prepares a model answer for each before asking):
1. Why does every command in a plan start with `# DRY RUN:` — what could go wrong if the copilot's output were run as-is, even by a careful person?
2. Why does `containment-bot.md` declare only the Read and Glob tools, and what would change about the project's safety claim if it also had Bash?
3. Why does "preserve evidence" come before revoking sessions and removing methods — what evidence is lost if the order is reversed?
4. Why revoke sessions AND disable the account — what does each one stop, and why is one of them not enough on its own?
5. Why remove only the newly added MFA method rather than all of the user's methods?
6. Why must the copilot never touch the break-glass accounts, how does it know which accounts those are, and what happens to an organisation that locks itself out of them?
7. Why are the answer keys written by you from Microsoft Learn instead of being generated by a model — what kind of error would a model-written key hide?
8. Why is the keyword scorer unreliable — give one plan that is correct but scores "missing", and one that is wrong but scores "present", from today's grading if possible?
9. Why is a plan that writes `TODO(verify)` for an unknown command better than one that invents a plausible command name?
10. Why run each model once on one batch of all incidents instead of once per incident, and what does that trade away?
