# T4-C1 — Class: 4E Canada-Only Landing Zone + 4H Secretless Deploy

Repo: td-4-cloud · Environment: td-4-cloud · Day: D8 · Time box: 60 minutes · Credit cap: $4

Eojin must be able to explain every file in `4e-canada-landing-zone/` and `4h-secretless-deploy/` to an interviewer without notes. This session is a lesson, then a "why" interview with honest grading, then one small live change done test-first. No code changes except the exercise and any bug Eojin finds. The summary goes to `docs/learning/T4-C1.md`.

## Steps
1. Director: read the 4E and 4H files once; keep a short summary; do not re-read them later.
2. Lesson part 1 (about 15 minutes), director explains in plain English, file by file: the two policy parameter files (what a policy is, Deny vs Audit effect, why resource groups need their own location policy, what happens to resources that already exist); the custom role (`Actions`, `NotActions`, `AssignableScopes`, why the placeholder); `BUDGET-AND-ALERTS.md` (what the activity log is); `SIGNUP.md`; `diagram.md`.
3. Lesson part 2 (about 15 minutes): `main.bicep` line by line (parameters, `uniqueString`, each security property); the OIDC flow as a numbered sequence (workflow asks GitHub for a token → token carries issuer/subject/audience → `azure/login` presents it to Entra → Entra finds the federated credential whose subject matches → short-lived Azure token → `az` commands); `deploy.yml` permissions; `cannot-do.yml` and why each step checks a specific error code; the subject format in `OIDC-SETUP.md`.
4. Interview (about 20 minutes): ask the ten questions below one at a time; wait for Eojin's answer; grade it honestly as correct / partly / wrong and only then give the model answer (prepared from the repo files; `TODO(verify)` where a fact is not in the repo). No hints before he answers. Record question, his answer in short, grade, and the one thing to remember.
5. Live change exercise (about 10 minutes), Eojin drives: he dictates each change in chat and Claude types it verbatim (`builder` only helps when he asks): add `allowSharedKeyAccess: false` to the storage account in `main.bicep` (this turns off the account's shared keys so only identity-based access works). Order: (a) add a test in `tests/test_4h_workflows.py` asserting the line exists; (b) run `pytest -q` and watch it fail; (c) make the change; (d) run `bicep build 4h-secretless-deploy/main.bicep --outfile /tmp/main.json` (or rely on CI if bicep is missing) and `pytest -q`; (e) commit on branch `t4-c1-class`. Discuss: what else would break if a tool relied on the storage key (answer: anything using a connection string).
6. `chores`: write `docs/learning/T4-C1.md`: lesson summary (ten lines), the ten Q&A with grades, the exercise result, and "to revisit before an interview".
7. Director: `wrap` — `verifier` writes `docs/verify/T4-C1.md`; `docs/RUN-SHEET.md` T4-C1 → DONE; `COSTS.md`, `AI-USE.md` (class entry), `docs/CAVEATS.md`; push branch `t4-c1-class`; print PR title and body.

The ten "why" questions (the director prepares a model answer for each before asking):
1. Why do the location policies use the Deny effect instead of Audit, and what happens to a resource that already sits in `westus` when the policy is assigned?
2. Why is a separate "Allowed locations for resource groups" policy needed when "Allowed locations" is already assigned?
3. Why require an `owner` tag at all — what question does it answer at 2 a.m. during an incident, and why does the policy not fix resources that already lack it?
4. Why does the custom role list `*/read` plus only three VM actions, and what is the practical difference between `powerOff` and `deallocate`?
5. Why is `AssignableScopes` a placeholder in the repository, and what could someone do with the real subscription ID if it were public?
6. Why alert on `Microsoft.Authorization/roleAssignments/write` specifically — which step of the takeover chain (fake call → reset → new MFA device → takeover → cloud damage) does it catch?
7. Why does OIDC remove the need for a stored secret — what exactly does GitHub give Azure, what three fields does Azure check, and how long does the resulting access last?
8. Why does the federated-credential subject include the owner ID and repository ID, and what could an attacker do if Azure only checked the names?
9. Why do the workflows declare `permissions: id-token: write, contents: read` and nothing else, and what would `contents: write` add to the risk?
10. Why does `cannot-do.yml` pass only on a specific error code (`RequestDisallowedByPolicy`, `AuthorizationFailed`) instead of "the command failed" — give one wrong-reason failure that a sloppy test would wrongly count as a pass?
