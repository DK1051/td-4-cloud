# T4-S02 — 4H Secretless Deploy: Bicep + OIDC workflow + cannot-do tests

Repo: td-4-cloud · Environment: td-4-cloud · Day: D3 · Time box: 120 minutes · Credit cap: $12

## Goal
Build a deployment that stores no password or key anywhere: a Bicep template for a locked-down storage account, a GitHub Actions workflow that logs in to Azure with OpenID Connect (OIDC: GitHub hands Azure a short-lived signed token that says "this is workflow X in repository Y on branch main", and Azure accepts it only if a pre-registered "federated credential" matches that exact identity), and a second workflow that proves what the deployment identity CANNOT do. Also write the setup guide Eojin follows by hand, including the one detail that silently breaks everything if it is wrong: the exact subject string for a repository created after July 15, 2026. The session only writes and validates files; Eojin runs the workflows himself after the merge.

- `docs/PROBES.md` shows whether `bicep` is installed. If it is not, the session continues and CI's `az bicep build` step is the validation (mark the related criterion NEEDS-EOJIN); this is not a stop.
- Nothing from Eojin's Azure side during the session. After the merge he needs the Azure free account (SIGNUP.md) and sets three GitHub Actions secrets himself: `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`. Their values never appear in any file, log or chat.

## Steps
1. Director: check Needs; run `bicep --version` (CAVEATS line if missing). In Plan mode, list the files below and the subagent for each; wait for approval.
2. `builder`: write `4h-secretless-deploy/main.bicep`: `param location string = 'canadacentral'`, `param owner string`, a storage account name built from `uniqueString(resourceGroup().id)` with a short prefix (3–24 lowercase letters and digits — a global-uniqueness rule), resource `Microsoft.Storage/storageAccounts` with SKU `Standard_LRS`, kind `StorageV2`, `supportsHttpsTrafficOnly: true`, `minimumTlsVersion: 'TLS1_2'`, `allowBlobPublicAccess: false`, `tags: { owner: owner }`. Output only the storage account name (never the resource ID: it contains the subscription ID and workflow logs are public). Use the newest API version that `bicep build` accepts without a BCP081 "unknown API version" warning; if bicep is unavailable, use `2023-05-01` and add `// TODO(verify): API version` on that line. Run `bicep build 4h-secretless-deploy/main.bicep --outfile /tmp/main.json` and quote the result (the compiled JSON is never committed).
3. `builder`: write `.github/workflows/deploy.yml` (name "4H deploy"): `on: workflow_dispatch` ONLY, with inputs `resource_group` (default `rg-td4-canada`) and `owner_tag` (default `eojin`); `permissions:` exactly `id-token: write` and `contents: read`; steps: `actions/checkout@v6`; `azure/login@v3` with `client-id: ${{ secrets.AZURE_CLIENT_ID }}`, `tenant-id: ${{ secrets.AZURE_TENANT_ID }}`, `subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}`; then `az deployment group create --resource-group <input> --template-file 4h-secretless-deploy/main.bicep --parameters owner=<input> --query properties.provisioningState -o tsv` (prints only "Succeeded"). No `push`, `pull_request` or `schedule` trigger. No other secret.
4. `builder`: write `.github/workflows/cannot-do.yml` (name "4H cannot-do"): `on: workflow_dispatch` ONLY, inputs `resource_group` (default `rg-td4-canada`) and `private_resource_group` (default `rg-td4-private`); same `permissions` and login as step 3; then three steps that each EXPECT failure. Shell discipline for each: capture output and exit code with `set +e` … `set -e`; if the command succeeded, print `FAIL: <what should have been denied>` and `exit 1`; if it failed, pass ONLY when the output contains the expected error code, else print `FAIL: failed for another reason: <error code only>` and `exit 1` — never echo the full error text (it can contain object IDs that are not masked). The three: (a) deploy `main.bicep` with `location=westus` → expect `RequestDisallowedByPolicy`; (b) `az role assignment create --assignee-object-id "$OID" --assignee-principal-type ServicePrincipal --role Reader --scope <the resource group's scope built from `az group show --query id -o tsv`>` → expect `AuthorizationFailed`, where `$OID` is the deploy identity's own object ID decoded in Python from the `oid` claim of `az account get-access-token --query accessToken -o tsv`, masked with `echo "::add-mask::$OID"` before first use and never printed (this avoids a Microsoft Graph lookup the identity can't make); (c) `az group show --name <private_resource_group>` → expect `AuthorizationFailed` or `ResourceGroupNotFound`. Pass when `grep -q '<expected code>'` matches the captured output (a denied deployment nests its code under `DeploymentFailed`, so never take the first code only); when printing a failure, show only the codes: `grep -o '([A-Za-z]*)' | sort -u | tr '\n' ' '`. Add `--output none` to every command whose output is not needed.
5. `builder`: write `4h-secretless-deploy/OIDC-SETUP.md` for Eojin, plain English, numbered, containing all of the following and nothing that is an ID: (1) what OIDC is in three sentences and why there is no stored secret; (2) Step A — get the two numbers from `https://api.github.com/repos/DK1051/td-4-cloud`: field `owner.id` and field `id`; keep them out of the repo (house rule), they go only into the federated credential; (3) Step B — Microsoft Entra ID → App registrations → New registration, name `td-4-cloud-github-oidc`, single tenant, no redirect URI; copy "Application (client) ID" and "Directory (tenant) ID" straight into GitHub secrets (Step D), nowhere else; (4) Step C, marked CRITICAL — Certificates & secrets → Federated credentials → Add credential → scenario **"Other issuer"** (NOT the "GitHub Actions deploying Azure resources" template, which may build the old name-only subject `repo:DK1051/td-4-cloud:ref:refs/heads/main`); issuer `https://token.actions.githubusercontent.com`; subject identifier `repo:DK1051@<OWNER_ID>/td-4-cloud@<REPO_ID>:ref:refs/heads/main` with both numbers filled and no spaces — this is GitHub's immutable subject format, used by repositories created after July 15, 2026 (source: https://docs.github.com/en/actions/reference/security/oidc); audience `api://AzureADTokenExchange`; name `github-main`; (5) **Never rename the repository after this**: the subject contains the repository name and renaming breaks the match; (6) Step D — GitHub → Settings → Secrets and variables → Actions → New repository secret, three times: `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID` (subscription ID from portal → Subscriptions); (7) Step E — first, once, as yourself in Cloud Shell: `az provider register --namespace Microsoft.Storage`, then repeat `az provider show --namespace Microsoft.Storage --query registrationState -o tsv` until it prints `Registered` (a few minutes; the deploy identity is not allowed to do this itself); then create resource group `rg-td4-canada` in `canadacentral` (after the 4E policies are assigned), give the app `td-4-cloud-github-oidc` the **Contributor** role on that resource group only (Access control (IAM) → Add role assignment → members: "User, group, or service principal" → search the app name), and create `rg-td4-private` in `canadacentral` too, with no assignment; (8) Step F — Actions tab → "4H deploy" → Run workflow on `main` → expect `Succeeded`; then "4H cannot-do" → expect three PASS lines; (9) Troubleshooting: `AADSTS70021` = no federated credential matches the token's subject (re-check owner ID, repo ID, branch; the workflow must run from `main`); `AADSTS700016` = wrong client or tenant ID; `AuthorizationFailed` on deploy = the Contributor assignment is missing or not yet propagated; `MissingSubscriptionRegistration` = the Step E registration isn't done yet; an optional debugging step: temporarily add a step using `actions/github-script` that calls `core.getIDToken('api://AzureADTokenExchange')`, base64-decodes the token's middle segment and prints only the `sub` claim, then remove the step; (10) Logs of a public repository are public: GitHub masks the three secret values, nothing else, so never paste raw workflow output into the README.

## Known caveats
- The immutable subject format (`repo:OWNER@OWNER-ID/REPO@REPO-ID:ref:refs/heads/main`, repositories created after July 15, 2026) is taken from the plan, which cites the GitHub docs page; Eojin confirms it on that page before creating the federated credential. A mismatch shows as `AADSTS70021` and is fixed by editing the subject, not by recreating anything.
- The federated credential pins branch `main`, so the workflows must be started from `main`; a run from any other branch fails to log in by design.
- Workflow logs on a public repository are public. GitHub masks only the three secret values; the deployment identity's object ID and the tenant's default domain can appear in raw Azure error text, which is why `cannot-do.yml` prints only error codes.
- PyYAML parses the workflow key `on:` as the boolean `True`; the tests must handle that or they silently test nothing.
- Cannot-do test (a) proves something only after the 4E "Allowed locations" policy is assigned and in force (propagation delay `TODO(verify)`).
- Azure CLI on GitHub runners installs the Bicep CLI on first `az bicep` use, so the CI step needs no extra install step; if the runner image changes, add `az bicep install` before the build.
- The deployed storage account is nearly free but not zero; Eojin deletes `rg-td4-canada` after the final class or keeps it for demos — his call, noted in the README.
